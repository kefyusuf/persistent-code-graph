# M1.6.2 — Canonical Persistent Store Migration

Status: **M1.6.2 verification PASS** (150/150 tests, including 16 real-grammar tests, in [GitHub Actions](https://github.com/kefyusuf/persistent-code-graph/actions/runs/41355996826)). Draft PR #4 remains open and unmerged.

## Scope

Move the already-tested M1.4 persistent object/snapshot/head implementation to one canonical owner under `src/storage/`, retaining its exported API and on-disk semantics. Do not introduce a new database, schema version, migration process, daemon, background writer, auto-refresh, or semantic relationship resolver.

## Ownership and compatibility

- `src/storage/store.mjs` is the sole implementation of `CodeGraphStore`, `compareManifest`, and `canonicalJSONString`.
- `spikes/m1.4/src/store.mjs` is an export-only compatibility shim: old imports resolve to **identical function/class objects**.
- Historical refresh (`spikes/m1.4.1/src/refresh.mjs`) and verified query (`spikes/m1.4.2/src/query.mjs`) import the canonical storage owner directly. Their logic is **not** moved or rewritten in this milestone.
- The public `src/index.mjs` / `src/core.mjs` API is unchanged and still orchestrates existing refresh and query modules.

## Persistence and freshness invariants

- Disk layout and snapshot schema version remain unchanged: immutable objects, immutable snapshots, checkout-specific heads, and exclusive writer locks.
- Canonical JSON and content hashes are unchanged; an existing snapshot can be read without migration or re-parsing.
- Reopening a store returns `freshness: 'unknown'`; persistence never implies source-code freshness.
- Head publication is atomic relative to a completed snapshot; injected failures do not replace the previous head. The orphaned lock and cross-platform durability limitations documented in M1.4 remain open.
- Separate checkout/worktree keys do not share a head, but identical file-fact blobs can be shared.

## Not claimed

Not a complete semantic code graph; no cross-file call resolution, universal language support, concurrent-writer recovery, Windows crash-consistency validation, storage compaction, latency guarantee, or token savings measurement. The new canonical store remains coupled to historical refresh/query modules until later separately gated migrations.
