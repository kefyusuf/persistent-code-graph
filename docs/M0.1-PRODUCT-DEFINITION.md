# M0.1 — Product Definition

**Working title:** Persistent Code Graph (temporary; not a brand decision)  
**Status:** Proposed baseline for review  
**Stage:** M0 — Definition only  
**Scope:** Provider-independent, language-extensible, local-first, evidence-based code intelligence

## 1. Problem statement

Coding agents repeatedly discover the same repository structure across tasks and sessions. They search filenames, inspect modules, trace imports, and reconstruct call relationships, even when the source has not materially changed. This consumes tool calls, input tokens, elapsed time, and attention. A one-time summary is insufficient because code changes, branches diverge, and incomplete or stale descriptions can mislead the agent.

We need a small, persistent, inspectable structural index of the *current working checkout*. It should be built once, reused across agent sessions, and refreshed only where source changes require it. Agents should query the index for focused, source-backed answers, not receive a full repository dump.

The goal is **reduce repeated discovery work without reducing correctness**. A token reduction that worsens task outcomes is not a success.

## 2. Product promise

> Index once. Refresh what changed. Return only what matters. Never silently present stale context as current.

“Index once” refers to the initial complete build. It does **not** mean the system never checks files again; freshness verification has a cost. “Refresh what changed” means unchanged source files must not be reparsed under normal compatible-cache conditions. Some graph-wide re-resolution may remain necessary in the first implementation.

## 3. Target users and jobs to be done

**Primary:** Developers who work with one or more coding agents on existing repositories, including agents joining a project after development has started.

**Secondary:** Tool authors who need a deterministic, agent-neutral way to ask where code lives and what depends on it.

Jobs:
1. Orient an agent to the active checkout without re-exploring the repository from scratch.
2. Locate definitions, references, imports, and callers with file/line evidence.
3. Determine which relationships might be affected by a local change or Git diff.
4. Reuse the same index across supported agent sessions and clients.
5. Detect and report index drift before answering a source-structure question.

## 4. In-scope capabilities

### 4.1 Initial build
- Discover eligible source files under an explicitly selected repository root.
- Respect Git ignore behavior by default, with a narrow, documented inclusion policy.
- Extract structural symbols and supported relationships using a deterministic parser.
- Persist file fingerprints, parser identity, symbol records, relationship records, provenance and coverage metadata.
- Record the source checkout identity and exact index snapshot identity.

### 4.2 Incremental refresh
- Identify added, modified, removed and renamed files. Renames may initially be processed as delete-plus-add.
- Reuse extraction outputs for unchanged content when cache/parser versions are compatible.
- Remove obsolete symbols and relationships and re-resolve affected references.
- Publish a complete, internally consistent graph snapshot atomically.
- Detect changes made outside the agent and changes not yet committed.
- Handle branch switches, commits, merges, rebases and worktrees as changes in checkout state, not merely as hook events.

### 4.3 Retrieval
- Provide compact queries for project overview, symbol lookup, callers, dependencies, references, and changed-code impact.
- Return file path, line range, source fingerprint/snapshot and relationship confidence where applicable.
- Limit results by an explicit response budget and allow bounded pagination/expansion.
- Prefer `unresolved` or `unknown` to inventing links in dynamically resolved code.

### 4.4 Access
- Keep a single index engine independent of coding-agent vendors.
- Supply CLI queries first; add a thin MCP read interface only after core behavior passes verification.
- Source code is never modified by an indexing or query operation. Internal index maintenance is permitted.
- Run core parsing, refresh and structural queries offline, without an LLM or external account.

## 5. Explicit non-goals (M0–M5)

- Agent long-term memory, session transcripts, prompt history or personal knowledge bases.
- LLM-generated project summaries, semantic embeddings, vector search, RAG, or model training.
- Autonomous code edits, refactoring, test generation, code review agents or PR commentary bots.
- Cloud synchronization, multi-tenant SaaS, user authentication, hosted dashboards or analytics.
- A visual graph explorer, IDE replacement, workflow orchestrator or agent marketplace.
- Full compiler-equivalent resolution for every language or framework.
- Multi-repository knowledge fusion. Each repository/checkout remains independently addressable.
- Indexing every programming language at launch; language extensibility is an architectural boundary, not immediate coverage.

Ideas outside these boundaries are recorded separately, never introduced as hidden prerequisites.

## 6. Sources of truth and freshness model

- **Truth:** Current on-disk source content in the selected checkout (including uncommitted edits and eligible untracked files).
- **Git metadata:** Commit/branch/merge-base information helps identify transitions, but is not a substitute for detecting working-tree modifications.
- **Index:** A derived cache, not an authority over source.
- **Freshness claims:** `verified` means the configured verification process has confirmed the indexed content; `uncertain` means it cannot substantiate that claim; `stale` means it has detected drift. No `uncertain`/`stale` answer may be silently labelled current.
- **Remote PRs:** A pull request is a remote event. A local index is updated for its checkout only when those source bytes are present locally. CI may build/check an index for the PR's checked-out head; remote PR activity alone never alters an unrelated local checkout.

## 7. User journeys / use cases

**UC-01 — First contact:** On an existing repository, a developer explicitly initializes the index. The system reports indexed files, symbols, relations, exclusions, parser coverage and current snapshot.

**UC-02 — New agent session:** A different agent accesses the pre-existing index and requests a small project orientation. No complete reparse occurs if the index is compatible and current.

**UC-03 — Local edit:** A developer changes one source file. The next freshness-sensitive request detects the drift, reparses the changed file only, updates affected relationships, and returns a verified new snapshot—or an explicit non-current status.

**UC-04 — Git transition:** Checkout, merge, rebase or pull changes the working tree. The engine reconciles the checkout rather than relying solely on a Git hook having run.

**UC-05 — Impact:** An agent asks what depends on a changed symbol. The engine returns bounded dependents with source evidence, plus coverage and uncertainty limits.

**UC-06 — Failure:** A parser or refresh fails. The engine preserves the last valid snapshot, reports it as stale/uncertain and does not present source-backed answers as verified current.

## 8. Success measures

**Correctness gates (hard requirements):**
- A compatible incremental refresh produces a structurally equivalent graph to a clean build on the same source snapshot, under a canonical comparison that ignores irrelevant serialization order.
- Unchanged compatible files are not reparsed during a single-file update.
- Deletes/renames do not leave dangling or falsely current symbol references.
- All structural answers identify their snapshot and source provenance.
- Stale or uncertain index state is visible and never misrepresented as fresh.
- The system can reopen its index after process exit without requiring a full parse of unchanged source.

**Performance measures (comparative, not invented promises):**
- Cold build time, warm no-change check time, single-file refresh time.
- Files parsed and reused; bytes read/hashed; graph resolution work; index size.
- Query latency, result payload size, tokens spent discovering the same facts without/with the index.
- Task success and answer correctness on identical repository questions/tasks.

Do not set a headline token-saving percentage until a reproducible baseline exists. Optimize for correctness first, then lower median and tail costs.

## 9. Operational and safety boundaries

- Local-first, offline core; no mandatory daemon, remote API, telemetry, or model key.
- Default read-only access to repository source; cache writes confined to an explicitly managed, ignored index location.
- Protect against concurrent refresh collisions and partial writes.
- Keep secrets and ignored/generated files out of the index according to documented exclusions.
- Report unsupported languages, unresolved calls and excluded paths as coverage limitations.
- No assumption that a local Git hook executes in every workflow or on every platform.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Stale graph after external edits | Freshness verification before source-sensitive queries; explicit status |
| Misleading static call graph in dynamic languages | Provenance, confidence/coverage labels, unresolved edges |
| Costly full-tree metadata scans | Measure; reuse fingerprints; separate cheap checks from stronger verification without overstating freshness |
| Parser/cache version mismatch | Explicit versioned invalidation and safe rebuild |
| Branch and worktree cross-contamination | Checkout-scoped graph identity and snapshot isolation |
| Concurrent agents writing to one cache | Single writer, atomic publication, repeatable reads |
| Scope creep | Non-goals and documented exception criteria |
| Token savings at the cost of poorer results | Correctness-first comparative benchmark |

## 11. M0 decisions and deliberate deferrals

**Locked:** Purpose, target user, one local structural graph per checkout, deterministic offline core, source-backed compact retrieval, no silent stale claims, no agent-specific ownership, minimal scope.

**Deferred until M1 planning:** Implementation language, parser/library, storage engine, first supported programming language, packaging, CLI command names and exact schema. These decisions require small feasibility spikes rather than assumptions.

**Deferred beyond the core:** Background file watching, GitHub Actions packaging, shared team index distribution, additional languages, graph UI, advanced semantic resolution.
