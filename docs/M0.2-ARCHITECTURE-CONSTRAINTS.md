# M0.2 — Architecture Constraints and Invariants

**Working title:** Persistent Code Graph  
**Status:** Proposed baseline for review  
**Stage:** M0 — Architecture constraints only  
**Dependency:** M0.1 Product Definition

## 1. Architecture principle

Build the smallest independent pipeline that can answer structural source questions from a persistent, current and inspectable graph. The indexing engine owns data; agent integrations are interchangeable, thin clients. No subsystem may introduce AI/cloud/stateful-agent requirements into core indexing.

```text
Current checkout (tracked, eligible untracked, uncommitted)
                     |
            File inventory + drift
                     |
        Deterministic parsing / extraction
                     |
       Symbol and relationship reconciliation
                     |
       Validated, atomically published snapshot
                     |
             Bounded query interface
                     |
                CLI / MCP adapters
```

This is a **logical** separation; it does not require separate services, packages, processes or databases.

## 2. Mandatory invariants

**INV-01 — Source authority.** On-disk eligible source is authoritative. Git commit SHA alone cannot establish content freshness because the working tree may be dirty.

**INV-02 — Persistence.** A fully built snapshot survives agent/process restarts. New sessions reuse it when compatible and verified; they do not automatically perform a cold parse.

**INV-03 — Incremental extraction.** For compatible parser and cache versions, unchanged content is not reparsed. A source change may cause broader relationship reconciliation; record both costs separately.

**INV-04 — Cold/warm equivalence.** The graph produced by incremental update must be structurally equivalent to a clean build for the same checkout and parser version.

**INV-05 — Provenance.** Every symbol and relation must have an identifiable source file and snapshot. Inferred or unresolved relations cannot be presented as compiler-verified facts.

**INV-06 — No silent staleness.** Each query reports its snapshot/freshness state. If fresh content cannot be established, the query explicitly marks its result uncertain/stale or declines to provide a current answer.

**INV-07 — Atomic publication.** Readers never observe a half-written graph. A failed update leaves the last valid snapshot available but not silently current.

**INV-08 — Checkout isolation.** Concurrent branches/worktrees must not overwrite each other's graph state. Shared parse caches are optional future optimization, not a prerequisite.

**INV-09 — Determinism.** Identical eligible source, configuration and parser versions produce equivalent logical graphs and stable ordering in query responses.

**INV-10 — Minimal context.** Queries are bounded; there is no automatic injection of the full graph, whole files or all edges into an agent prompt.

**INV-11 — Offline core.** Building, checking, updating and structural querying require no cloud connection, model calls, telemetry service or external database server.

**INV-12 — Repository safety.** The engine reads repository content but never alters user source, commits, branches, hooks or project instructions without a separate explicit installation action.

## 3. Minimal logical records

Do not lock to any database representation at M0. These are conceptual contracts, not final tables:

| Record | Required conceptual fields |
|---|---|
| Repository | Canonical root and repository identity |
| Checkout | Working-tree location, Git state and isolation identity |
| Snapshot | ID, parser/config versions, indexed content manifest, creation and verification state |
| File | Normalized relative path, eligible language/type, content hash, metadata and coverage |
| Symbol | Stable-in-snapshot ID, qualified name, kind, file path, source range and provenance |
| Edge | Relation kind, source and target or unresolved target, resolution confidence and evidence |
| Index status | Current, building, updating, stale, uncertain or failed; reason and snapshot ID |

Symbol IDs must be deterministic within a snapshot. Cross-rename semantic identity preservation is **not** required in the initial release; delete-plus-add is valid if old edges are retired correctly.

## 4. Lifecycle and states

```text
UNINITIALIZED --explicit init--> BUILDING --success--> READY
                                       | failure
                                       v
                                     FAILED
READY --detected drift--> STALE --refresh--> UPDATING --success--> READY
                                 ^              |
                                 |              | failure
                                 +--------------+
```

`READY` is a snapshot state, not proof that no source edit occurred after the last check. A freshness-sensitive query performs its configured verification step and communicates its level of assurance.

### Freshness levels

- **Verified:** Current source manifest was checked under the declared verification method, and the query references that snapshot.
- **Metadata-checked:** Size/mtime or change events indicate no drift, but content equality was not conclusively established. Do not label this level content-verified.
- **Stale:** A concrete source mismatch or invalidation is known.
- **Unknown:** Required verification failed or could not complete.

**Terminology mapping (design vs. implemented file-facts query):** M0.1's prose term `uncertain` and this section's **Unknown** describe the same inability to substantiate freshness; they are not two independent freshness levels. In the M1.6 query result, `state: 'unknown'` reports this case, `state: 'stale'` reports detected drift, `state: 'verified'` means a point-in-time double content-hash check succeeded, and `state: 'missing'` means no stored snapshot exists. A lifecycle `READY` snapshot is **not** automatically a freshness-verified query. **Metadata-checked** is a design possibility, not an implemented M1.6 query state. This mapping is explanatory; it does not introduce new public fields or broaden the supported states.

For an exact freshness guarantee, a content hash comparison (or an equivalently trustworthy change journal) is required. Size and mtime alone can miss modifications. Re-hashing has an I/O cost, distinct from reparsing. The first version must expose this tradeoff honestly, not claim that a cheap stat check proves byte-for-byte freshness.

## 5. Index and refresh algorithm (behavioral contract)

**Initial index:**
1. Identify the checkout and approved source inventory.
2. Parse eligible files and extract file-local symbols/raw references.
3. Resolve supported cross-file relations and record unresolved cases.
4. Validate node/edge integrity and coverage.
5. Write a new snapshot atomically with source manifest and parser/config identity.

**Incremental refresh:**
1. Enumerate current eligible files and compare against the persisted manifest (including uncommitted and eligible untracked changes).
2. Classify unchanged, added, modified and removed paths; rename detection is optional.
3. Reuse extraction cache only when file content hash, parser identity and extraction schema match.
4. Reparse added/modified files; remove obsolete records from changed/deleted files.
5. Reconcile impacted relations; the first correct implementation may perform global relation re-resolution over cached extraction outputs.
6. Validate resulting graph against the intended source manifest.
7. Atomically publish a new snapshot or retain the previous snapshot with an explicit failure/staleness status.

A no-op refresh must reparse zero files. A file whose bytes did not change must not be reparsed solely because it was touched, provided the content check proves equivalence.

## 6. Git and PR semantics

- **Local edit/save:** The on-disk content, not a commit event, drives refresh.
- **Commit:** A commit with unchanged working-tree source typically changes version metadata; do not rebuild just to respond to the word “commit.”
- **Checkout/merge/rebase/pull:** Compare the resulting source tree with the persisted manifest; reparse only content changed relative to the active checkout snapshot.
- **Worktree:** Give each checkout an independent published graph and freshness record; no path ambiguity.
- **Pull request opened/updated:** A remote PR does not itself modify a local checkout. A CI checkout may index the exact PR head or compare it with its merge base; this is a later integration, not a core dependency.
- **PR merged:** Main-branch checkouts refresh when their source tree receives the merged content; CI may verify the merged commit separately.
- **Missed hooks:** Hooks are performance hints only. Source verification on query/manual refresh is the correctness backstop.

Do not implement automatic Git hooks or background watchers in M1. They can be added as adapters later only after the core refresh contract is reliable.

## 7. Query contract

Each supported query returns:
- Query kind and bounded result set, with deterministic ordering.
- Snapshot identifier and freshness assurance level.
- Matching names/kinds and precise relative path/line evidence.
- Relation confidence (`resolved`, `inferred`, or `unresolved`) and coverage notes, where applicable.
- A result limit or cursor so users/agents expand only when required.

The core query contract is independent of MCP, agent host or LLM provider. A CLI adapter tests the behavior first. The future MCP adapter must not maintain an alternative index or silently expand response budgets.

## 8. Complexity and dependency budget

1. One repository-indexing core; no additional microservices, hosted graph servers or mandatory daemons.
2. Minimal persistent store selected by measured needs, not graph-database branding.
3. No network calls, LLM, embeddings, vector indexing or knowledge-memory pipeline in core.
4. No per-agent graph copies. Integrations are wrappers around the same query contract.
5. No auto-generated repo instructions or hooks during `index`; installation/wiring is an explicit separate action.
6. No cross-repo graph unification, analytics dashboard, GUI or policy engine.
7. No performance optimization that weakens cold/warm correctness equivalence without an explicit, measured tradeoff.
8. Any proposed new dependency/feature must demonstrate a correctness, freshness or context-efficiency benefit with an acceptance test.

## 9. Test and verification plan

**Fixture categories:** symbols/imports/calls, ambiguous resolution, deletions, renames, edits with unchanged size/mtime, ignored/untracked files, parser errors, branch switches, merge conflicts, worktrees, concurrent readers/updater, process interruption and schema upgrade.

**Mandatory tests:**
- Cold index vs incremental index logical graph equality.
- No-change recheck => zero files reparsed.
- Single modified file => only that file reparsed, except when the parser contract explicitly invalidates more.
- Removed symbol => no stale active edge pointing at it.
- Content altered with same size/mtime => strong verification detects drift.
- Failed update => no partial snapshot; status reports failure/staleness.
- Two agents/readers => same committed snapshot and bounded query results.
- Worktree B source changes => worktree A index unaffected.
- Unsupported/dynamic relation => no invented high-confidence edge.
- Source code bytes and Git refs unchanged by indexing/querying.

**Benchmarks:** The same repository questions and implementation tasks, with/without the index, scored for answer correctness/task completion first, then token usage, latency and tool calls. Isolate initial indexing cost from per-task cost and report amortization over multiple tasks.

## 10. Milestone gates

**M0 (now):** Product Definition and Architecture Constraints accepted; terms, invariants, non-goals and test protocol frozen. No language/runtime/storage decision required.

**M1 — Single-language deterministic index:** One supported language, an inspectable persistent snapshot, CLI to inspect status and symbols, clean-build reproducibility; no MCP or watcher.

**M2 — Incremental refresh:** Working-tree drift detection, parse reuse, delete/rename handling, atomic updates, cold/warm equivalence and explicit freshness.

**M3 — Git awareness:** Commit/branch/merge/rebase/worktree behavior validated. PR/CI integration remains optional and separate from local correctness.

**M4 — Bounded graph queries:** Callers, dependencies and references with provenance, confidence and coverage.

**M5 — Agent adapter:** At least two MCP-compatible clients use the same index; no per-agent index logic.

**M6 — Evaluation:** Reproducible correctness, token, latency and cost comparisons; adoption decision based on actual net benefit.
