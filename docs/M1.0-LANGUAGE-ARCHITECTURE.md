# M1.0 — Language Detection and Structural Extraction Architecture

**Project:** Persistent Code Graph (working title)
**Status:** Design proposal; not implemented
**Stage:** M1 technical design (no implementation or storage selection)
**Depends on:** M0.1 Product Definition and M0.2 Architecture Constraints

## 1. Design objective

Support repositories containing JavaScript, TypeScript, Python, PHP, Rust, C#, and additional languages **without adding language-specific conditionals to the indexing core**. Distinguish reliable syntax extraction from harder project-aware semantic resolution. A parser grammar is not a compiler, a package resolver, or a source of runtime truth.

**Principle:** Language-specific grammar and extraction, language-neutral graph contracts, one shared freshness and persistence engine.

## 2. Minimal conceptual pipeline

```text
checkout inventory (.gitignore, approved overrides)
  -> file classification (language + dialect + embedded segments + evidence)
  -> parser registry (grammar + extractor/query pack)
  -> file-local facts (definitions, imports, raw references, uncertain calls)
  -> shared symbol table and relationship resolver
  -> normalized graph with evidence and coverage
  -> validated, atomic snapshot
  -> bounded CLI queries, then thin MCP adapter
```

This is a logical separation, not a requirement for microservices, plugins loaded from the network, an external database, or runtime daemons.

## 3. File language detection

File classification is performed **per file**, not by assigning one language to the entire repository. A checkout may contain PHP + TypeScript + Blade, or C# + JavaScript + Razor.

Suggested evidence order:

1. Explicit project configuration overrides; optionally `.gitattributes` language annotations.
2. Known exact filenames and filename suffixes (e.g. `.tsx`, `.pyi`, `.blade.php`).
3. Shebang and recognized editor modelines for extensionless/ambiguous files.
4. Lightweight content heuristics for unresolved ambiguous cases; do not silently guess.
5. Package and build manifests for **package/module context**, compiler flags, and dialect, not as a replacement for file classification.

In the **proposed classification contract**, return `language`, `dialect`, `detectedBy`, `confidence`, and `classificationStatus` (`classified`, `unknown`, `excluded`, or `unsupported`). Keep this status separate from **per-feature extraction `coverage`** as modeled in M1.1, and represent `parse_error` in parser `diagnostics[]` plus failed extraction coverage when applicable. A file excluded before parsing must not be described as a parse failure; an unsupported adapter must not be described as having complete coverage. These are conceptual fields, **not** a claim that the current M1.6 file-facts implementation persists excluded or unsupported records.

| File family | Initial classification | Context hints |
|---|---|---|
| `.js`, `.mjs`, `.cjs`, `.jsx` | JavaScript, with JSX dialect as appropriate | `package.json`, package boundaries |
| `.ts`, `.tsx`, `.mts`, `.cts` | TypeScript or TSX | `tsconfig.json`, workspace configs |
| `.py`, `.pyi` | Python / Python stub | `pyproject.toml`, source roots |
| `.php` | PHP | `composer.json`, PSR-4 mappings |
| `.rs` | Rust | `Cargo.toml`, crate/module roots |
| `.cs` | C# | `.csproj`, `.sln`, project references |
| `.go` | Go | `go.mod`, `go.work` |

Template/container files (`.vue`, `.svelte`, `.blade.php`, `.razor`) **must not** be silently treated as fully parsed ordinary source files. Before embedded-language support exists, report them as recognized but partially supported or unsupported with explicit coverage.

Exclude binary, generated, vendored, dependency and ignored content by a documented policy. Respect Git ignore semantics and keep explicit overrides narrowly scoped. File inventories include eligible untracked and modified files, not solely HEAD.

## 4. Language adapter contract

An adapter is a small internal module consisting of a pinned grammar, declarative Tree-sitter query patterns, and minimal extraction rules. One adapter is not an independent indexer, service, cache, agent, or database.

Conceptual interface (non-executable):

```text
LanguageAdapter:
  languageId
  supportedDialects
  grammarVersion
  extractorVersion
  classify(filePath, context) -> match | no_match | ambiguous
  extract(source, dialect) -> FileFacts + Diagnostics
  capabilities -> feature coverage flags
```

`FileFacts` is a language-neutral structure:

```text
FileFacts:
  definitions[]: { kind, qualifiedName, localName, location, modifiers?, evidence }
  imports[]:     { specifier, alias?, location, evidence }
  references[]: { name, scopeId, location, category, evidence }
  relations[]:  { kind, sourceId, rawTarget, location, confidence, evidence }
  diagnostics[]: { code, severity, location? }
  coverage:      { definitions, imports, references, calls, inheritance }
```

The shared core is responsible for file inventory, hashing, cache reuse, versioning, snapshot publication, indexing concurrency, query budgets, and output schema. A separate optional resolver per language may be added for language-specific module lookup. This resolver must not invent a definite edge from a mere name coincidence.

## 5. Graph vocabulary and evidence

Base node kinds: `file`, `module`, `namespace`, `class`, `interface`, `trait`, `struct`, `enum`, `function`, `method`, `type`, `constant`. Keep dialect-specific kinds in optional typed metadata instead of multiplying core graph tables prematurely.

Base relation kinds: `contains`, `imports`, `exports`, `references`, `calls`, `extends`, `implements`. Reserve additional relations until a concrete fixture and query require them.

Each fact records: path, source range, source hash, snapshot, language, grammar/extractor identity, and evidence origin. A relation with a missing or ambiguous target remains `unresolved` (or an explicitly `inferred` candidate); only defensible source-backed associations are `resolved`. A syntax-derived call expression **does not automatically imply** a known concrete callee.

Stable IDs only need to be deterministic within the snapshot. Rename continuity across snapshots is not required by M1.

## 6. Language-specific boundaries

| Language | Syntax extraction | Main semantic limitations / later resolver inputs |
|---|---|---|
| JavaScript / TypeScript | imports, exports, classes, functions, methods, direct calls | path aliases, package exports, overloads, dynamic imports, JSX/TSX, prototype/runtime dispatch, type checker needed for precise targets |
| Python | modules, classes, `def`/`async def`, imports, calls | dynamic imports, decorators, monkey patching, runtime attribute lookup, source root/package rules |
| PHP | namespaces, classes, interfaces, traits, functions/methods, `use` | Composer PSR-4, traits, late static binding, Laravel container/facades, dynamic dispatch, Blade mixed content |
| Rust | crates, modules, structs, enums, traits, `impl`, `fn`, `use` | macros, `cfg` compilation, trait method resolution, generic specialization, Cargo workspace |
| C# | namespaces, types, interfaces, methods, `using` | partial classes, extension methods, overload resolution, project references, conditional compilation, reflection, Razor |

For all five languages, obtaining a syntax tree is **baseline structural coverage**, not full semantic coverage. High-confidence reference/call resolution may optionally use local language tooling or imported precise indexes in later phases, with no requirement that M1 install or start an LSP.

## 7. Index cache and incremental design

Cache key for each file's extracted facts:

```text
(contentHash, languageId, dialect, grammarVersion, extractorVersion, extractionSchemaVersion, relevantConfigHash)
```

For each change:
1. Identify eligible added/modified/deleted files; a rename may be delete-plus-add.
2. Keep cached extraction for unchanged content with matching adapter/cache identity.
3. Parse only changed or newly eligible files. Remove obsolete facts for deleted files.
4. Reconcile relations that may have been affected by changed definitions/imports/exports. In the first correct version, global re-resolution over cached file facts is acceptable.
5. Compare with a clean rebuild on the same source snapshot using canonical normalized graph equality.
6. Atomically publish on success. Preserve prior snapshot with explicit stale/failed status otherwise.

**Do not conflate:** Tree-sitter's incremental parse of edited syntax trees; the repository-level reuse of unchanged file facts; and graph-level incremental relation reconciliation. They are different optimizations with different correctness conditions.

### Language/version invalidation

Changing an adapter, grammar or relevant module configuration only invalidates the affected extraction/resolution scope. Global invalidation is permissible for correctness until selective logic has been measured. Track cache misses and their causes. When configuration changes cause no source change, the structural facts may remain valid while import resolution requires recomputation.

## 8. Mixed-language and cross-language edges

A project is a set of file-language records and package/module roots, never one global language label. Cross-language edges are recorded only when justified by explicit, inspectable source evidence (for instance a declared generated client contract or documented configuration); endpoint names, filenames, or coincidental function names alone are insufficient.

An API implemented in PHP and consumed from TypeScript may be visible as two independent subgraphs in the initial version. A full PHP-to-TypeScript runtime call edge is **not** implied merely because the repository contains both sides. This deliberate limitation prevents false confidence.

## 9. M1 scope and sequencing

M1 retains the M0 promise: **one language, a deterministic persistent graph, and CLI inspection, without MCP or watchers**. The general adapter boundary and capability flags are designed now, but multi-language implementation is staged. The first supported language and implementation/runtime/storage technology remain pending a small measured feasibility spike.

Proposed validation ladder (not launch commitment):
1. One language fixture: definitions, scopes, imports, raw calls, unresolved references, parser errors.
2. Second very different grammar in a test spike to validate adapter neutrality (not necessarily a product release).
3. Follow-on adapters as separate scoped increments after M1/M2 correctness gates; mixed-language support then tested explicitly.
4. Optional precise-resolution adapters only after deterministic baseline and cost/correctness benchmarking.

## 10. Acceptance fixtures and quality gates

- Monorepo with TypeScript UI, Python service and C# tool: classify every eligible file independently and do not guess missing semantic edges.
- `.tsx` uses the TSX grammar; `.blade.php` is recognized as a template, not presumed ordinary PHP.
- Extensionless Python script with valid shebang is recognized, while truly ambiguous content is flagged.
- `.gitattributes` explicit language override wins according to documented precedence.
- File content unchanged after touch -> no reparse under verified content identity.
- PHP class rename and import modification invalidate affected relations without stale active edges.
- C# partial class symbols remain consistently represented even when their semantic merging is not yet supported.
- Rust macro-heavy file reports limitations rather than fabricated concrete call targets.
- Parser syntax error produces a diagnostic and coverage marker; index remains valid or refresh fails explicitly according to established policy.
- Cached/incremental output matches cold-build normalized graph on the same source and versioned configuration.
- No source files, Git refs, branch names or agent instructions are modified by indexing.
- Every returned source fact includes evidence, version and freshness, and bounded query output.

## 11. Explicit deferrals / non-goals

Do not build a universal grammar; fork compiler frontends; add LLM-generated summaries, embeddings, vector DB, graph DB server, language auto-installation, runtime execution, generated language SDKs, code editing, background watchers, automatic Git hooks, auto-PR review, dashboards or cloud coordination as part of M1. Optional LSP/SCIP input is a later separate decision, not a hidden requirement.
