# M1.4 — Persistent Index Store Feasibility Spike

**Working project:** Persistent Code Graph  
**Date:** 2026-11-01  
**Status:** Independent storage feasibility **PASS** (18/18 local tests); production acceptance **NOT GRANTED**.  
**Prerequisite note:** M1.3 real Tree-sitter grammar compatibility remains **BLOCKED** by unavailable npm packages. The M1.4 experiment is intentionally decoupled from the parser; it must not be used to imply M1.3 is complete.

## 1. Decision and objective

Evaluate the smallest durable, local, deterministic persistence boundary that lets multiple agent sessions read the same checkout's indexed facts without rerunning parsing. Test preservation on restart, idempotence, per-file immutable reuse, atomic snapshot publication, checkout isolation, corruption detection, and concurrent-write refusal. **Do not** select a production datastore, implement parsing/resolution, connect to Git, install hooks, or expose MCP.

This experiment uses only Node.js built-in modules and **no npm dependencies**. Its use of JavaScript is a spike implementation choice, **not** a decision that the production indexer must be implemented in JavaScript or Node.js.

## 2. Minimal data layout

```text
<external-index-root>/
  objects/<sha256>.json          # immutable, canonicalized file-local facts
  snapshots/<sha256>.json        # immutable references to file-fact objects
  heads/<checkout-key>.json     # one atomic publication pointer per checkout
  locks/<checkout-key>.lock/    # exclusive writer admission
```

The index root must be **outside** the repository under inspection. This avoids modifying source directories, creating accidental untracked files, or silently changing `.gitignore`. The checkout key is derived from the canonical existing checkout directory path. Different worktree paths receive distinct heads. Equal file-fact objects can be shared across worktrees under one object root.

Each file-fact object includes its relative source path, source-content SHA-256, language, parser cache identity, declaration/reference/diagnostic arrays, and coverage metadata. A snapshot identifies a complete, ordered set of these immutable objects and the checkout key. The current head points at exactly one snapshot.

This is **not** yet an actual source-code graph; M1.4 persists file-local facts and empty/unresolved relations produced by a future extractor. Cross-file graph resolution remains out of scope.

## 3. Publication algorithm

1. Validate paths, file-fact shapes, source hashes (format only), and parser cache identity (format only); reject duplicates.
2. Acquire an exclusive per-checkout writer directory lock. Refuse a second writer rather than racing.
3. Check the caller's expected current snapshot ID under the lock (compare-and-swap); refuse stale writers.
4. Canonically serialize each file's facts; reuse existing content-addressed objects when identical, otherwise write them with a same-directory temporary file and atomic rename.
5. Write a deterministic, immutable snapshot object referencing only committed file-fact objects.
6. Atomically replace the checkout head pointer after all referenced objects are available. A failure before this point leaves the previous head in place.
7. Release the writer lock.

Readers load the head **once**, then the immutable snapshot and the referenced objects. Each loaded object's bytes must match its SHA-256 filename. Invalid or missing references fail with an integrity error, not a fake empty index.

**Crash/durability qualification:** Atomic rename prevents partial-file visibility on the tested local filesystem; durability across power loss and rename semantics on Windows/network filesystems have **not** been experimentally verified. Directory fsync is best-effort. Failpoint tests cover interruption before head publication, not arbitrary power failures.

## 4. Freshness vs persistence

Loading data from the store returns `freshness: "unknown"`, even when the store is internally consistent. This is deliberate. Persisted data can be correct for an older checkout and still be stale relative to disk.

`compareManifest(before, after)` uses source-content SHA-256 **and** parser cache identity to classify added, changed, removed, and unchanged file records. It does **not** traverse the working tree or claim its inventory is exhaustive. Only a future inventory/verifier can promote freshness to a verified level. File size/mtime must never be described as byte-level proof.

For a changed source, new file-fact content is stored separately. An unchanged file object is reused, while the snapshot manifest changes. This reduces storage churn; it does **not** demonstrate that parsing or cross-file relation resolution is incremental, because neither is part of this spike.

## 5. TDD evidence

| Phase | Evidence | Outcome |

The 18 tests cover:

- Persistence and read after reopening a store instance.
- Deterministic repeated publication and no-op snapshot identity.
- Object reuse after a single source change.
- Simulated failure after snapshot staging, before head publication.
- Corrupted object and corrupted head rejection.
- Compare-and-swap refusal for stale writer expectations.
- Different heads for two checkout directories with shared immutable objects.
- Duplicate/path-traversal rejection and invalid file-fact rejection.
- Source hash manifest comparison for additions, removals, modifications, and no-op.
- Read-only `freshness: unknown` on load.
- Canonical JSON key ordering.
- Exclusive writer lock refusal.
- Parser identity change invalidates a file's cache key.
- Tampered snapshot rejection.
- Removal from the new snapshot without rewriting the historical snapshot.
- Refusal to place the store inside the source checkout.

No benchmark under realistic repository size was performed. The test counts and timings cannot be used as evidence of token savings, memory scalability, or general-purpose throughput.

## 6. Caveats / non-goals

1. **M1.3 BLOCKED:** real WASM grammars still not installed or executed. No grammar gate has been passed.
2. **No actual indexer:** tests use synthetic file-fact records; no real source inventory, parser, or symbol resolver is connected.
3. **No semantic edges:** this does not establish call-graph accuracy or correct incremental edge reconciliation.
4. **No snapshot GC:** historical snapshots and orphaned immutable blobs can accumulate. GC is a later, separately justified capability.
5. **Crash-orphaned lock:** on a hard process crash, an abandoned `*.lock` directory remains and subsequent writers fail closed until an operator establishes there is no active writer and removes it. No unsafe automatic lock stealing.
6. **No optimistic read freshness:** validation of referenced object contents cannot establish that checkout source bytes are unchanged.
7. **Cross-platform pending:** tests were executed only on the current Linux container, with Node.js 22.16.0. Windows lock, filesystem, and path behavior require a separate gate.
8. **Large-repo performance unknown:** publication currently canonicalizes supplied facts for every file to compute IDs; it avoids rewriting existing objects, not the in-memory work of processing all supplied facts.
9. **Checkout identity:** absolute realpath is adequate for this experiment, but path relocation, case sensitivity, symlink transitions, file permissions and repository identity across clones need dedicated design.
10. **No distributed guarantees:** network FS and cloud object storage semantics not tested and not in scope.

## 7. Architecture evaluation

**Preserved:** source authority, persistence across sessions, conservative freshness, deterministic serialization, checkout isolation, atomic head publication, offline core, and no repository modification.  
**Not demonstrated:** real parser integration, content-verified working-tree freshness, incremental extraction, cold/warm graph equivalence, production performance, cross-platform durability and agent usage.

**Minimality assessment:** A local directory plus content-addressed JSON is a useful baseline for early testing and keeps the implementation inspectable. No graph database or embedded SQL engine is justified yet. This does **not** lock future storage to JSON. When realistic graph size and query workloads exist, compare this model with a simple SQLite store using measured read, write, memory, and recovery costs.

## 8. Follow-up gates

**Gate G1 — Complete M1.3:** Run the 12 real grammar tests with pinned, locally installed `web-tree-sitter` and PHP/TypeScript/TSX WASM assets, produce lockfile and SHA-256 grammar evidence, and run the Windows/Linux matrix (with failures recorded, not silently skipped).

**Gate G2 — Integrate parser and store (proposed M1.5):** Feed real M1.3 normalized facts to the M1.4 store, reopen in a new process, assert zero reparse on unchanged compatible input, reject parser version drift and byte-changed source, and prove cold/warm equivalence at the file-fact level.

**Gate G3 — Production persistence choice:** Compare JSON object store against a minimal embedded alternative on measured realistic workloads. Add writer recovery, integrity migration and storage growth policies only if justified by evidence.

**Decision:** Archive M1.4 as a successful, parser-independent storage **spike**, not as a passed production architecture or a reason to bypass the blocked M1.3 gate.
