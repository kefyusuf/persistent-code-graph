# M1.6.13 — Managed Storage Path Symlink Guard

**Scope:** static pre-operation storage path validation. The index remains an offline, content-addressed, explicit-refresh file-facts store.

## Reproduced defect

M1.6.7 canonicalized the `indexRoot` at construction, but `publish()` could still follow pre-existing symlinks named `objects/`, `snapshots/`, `heads/`, or `locks/` beneath that safe root. Each can point into the source checkout, causing writes there in violation of the storage boundary. A previously absent index root could also be replaced with a symlink after store construction.

## Repair

- Reject symlinked or non-directory managed subpaths at the start of **both** `read()` and `publish()`, before any store mutation.
- Re-resolve the canonicalized index root at these entrypoints. Reject an unexpected new symlink or redirection, including into the checkout.
- Allow absent subdirectories to be created by the existing publication process; preserve a safe symlink alias supplied as the original root, already physically canonicalized by the constructor.
- Keep existing snapshot IDs, manifest schema, lock behavior, query semantics, parser and cache identities unchanged.

## Verification

Six regression tests in `test/storage-boundary.test.mjs`: four managed-directory links, linked heads on read, and root replacement after construction. These reuse the existing M1.6.7 offline gate. RED commit `9606c217` introduced the failing behavior checks; final GREEN acceptance requires exact-head full GitHub Actions with no skipped real grammar tests.

## Limitation

This check is **not a race-resistant security boundary**. An adversarial process can change a directory after the check and before a filesystem operation. Directory-handle-based confinement and Windows-specific validation remain separate, unimplemented work. No production-readiness claim or new parser languages, graph resolver, MCP, daemon, cloud runtime, or data format is introduced.
