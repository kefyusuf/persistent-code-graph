# M1.5.1 — Verified Batch Queries

**Date:** 2026-11-01  
**Status:** **ACCEPTED as an independent offline performance/contract spike only**. M1.3 and M1.5 real Tree-sitter gates remain blocked.  
**Scope:** bounded, read-only, single-invocation queries against an existing persistent file-fact snapshot. No new parser, resolver, MCP tool, daemon, Git hook, cloud storage, automatic refresh, or LLM features.

## Motivation

M1.4.2 verified every independent query by hashing all eligible files twice. `N` sequential queries therefore trigger `2N` complete inventory scans. This is correct within its point-in-time assumptions but inefficient when an agent asks several related questions about the same project.

**Decision:** provide `verifiedQueryBatch` and expose it through the M1.5 pipeline as `queryBatch(requests, options)`. Reuse M1.4.2's inventory, drift, result selection, output caps, and integrity checks rather than inventing a new query or indexing engine.

## Bounded contract

- Between 1 and 8 requests per batch.
- Supported operations: `status`, `declarations`, `references`, `outline`, using the same selectors as M1.4.2.
- Each request retains its existing result-count (1–25) and result-byte (240–16,384) limits.
- One shared **serialized result arrays** budget: `maxTotalResultBytes` defaults to 8,192 bytes, with maximum 32,768. This is **not** a cap on the outer JSON envelope, diagnostics, or field names.
- The whole batch shares one start and one end source inventory check, plus a read of the immutable snapshot before and after execution.
- If either source inventory check fails or any eligible source changes, no draft query facts are returned. If the index head changes, the entire batch is stale.
- Queries never invoke the parser or write the index. A batch never implicitly refreshes the index.
- The result preserves `parserProvenance` and `semanticGraph: false` when accessed through the pipeline.
- `verified` remains point-in-time and cannot guarantee that files will remain unchanged after returning.
- No result is evidence that a symbol is globally absent; completeness is still partial.

## Example (experimental provider only)

```js
const reply = await app.queryBatch([
  { operation: 'declarations', name: 'Invoice' },
  { operation: 'references', role: 'call' },
  { operation: 'outline', file: 'src/invoice.php' },
], { maxTotalResultBytes: 8192 });

if (reply.state !== 'verified') {
  // Do not consume provisional facts; request an explicit refresh or retry.
}
```

## Limits and explicit non-goals

1. True Tree-sitter grammar compatibility remains unverified because npm DNS access fails with `EAI_AGAIN`.
2. This is a file-fact query layer, **not** a semantic call graph or validated cross-file symbol resolver.
3. The batch reads/hashes eligible files twice; amortization reduces scans across a group of questions but does not remove per-batch `O(total source bytes)` I/O.
4. The total budget counts serialized result arrays, not the whole response object; this should be documented if exposed over MCP later.
5. Under severe byte-budget pressure, a later query may receive fewer or zero results. The result's `truncated` field is mandatory; clients must not interpret truncation as absence.
6. Multi-process source and index races remain subject to the same point-in-time limitations as M1.4.2.
7. Windows and real-repository performance have not been validated.

## Architectural self-review

- **Single purpose:** reduces redundant *verification work* without adding a separate indexing path.
- **Truth:** source remains authoritative; any visible drift withholds the entire batch.
- **Reusability:** uses same query selection and caps as the existing contract; no parallel search engine.
- **Complexity bound:** a single new export and an M1.5 pipeline entrypoint; no persistent caching of asserted freshness.
- **Risk:** guard against false claims that local elapsed-time improvement equals token savings or broader graph correctness.
