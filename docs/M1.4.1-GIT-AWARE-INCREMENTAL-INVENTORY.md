# M1.4.1 — Git-aware Source Inventory and Incremental File-Fact Reuse

**Project:** Persistent Code Graph  
**Date:** 2026-11-01  
**Status:** Independent, parser-neutral feasibility **PASS (21/21 local tests)**; production integration **NOT ACCEPTED**  
**Prerequisites:** M1.4 storage spike PASS; M1.3 real Tree-sitter grammar compatibility STILL BLOCKED.

## 1. Problem and scope

Demonstrate that existing Git source trees can be checked by *content*, compared with persisted extraction records, and updated without re-extracting unchanged source files. This must not assume that a Git commit indicates a content change. Explicit refresh only: no MCP, background daemon, hooks, watchers, UI, cloud, embedding, vector database, or relation resolver.

The spike is implemented as two small modules and one optional experimental adapter:

- `src/inventory.mjs`: Git working-tree enumeration, language eligibility, whole-file SHA-256 and fatal UTF-8 validation; re-scan before publication.
- `src/refresh.mjs`: manifest comparison, per-file cache reuse, parse callback for changed files, store publish via M1.4's immutable objects and CAS head.
- `src/experimental-adapter.mjs`: M1.2 TypeScript Compiler API / native PHP tokenizer wiring used **only** to prove actual declarations survive persistence. **Not a Tree-sitter substitute or production language-support claim.**

No new npm runtime dependencies were added in this spike. Node.js 22 and Git are required, and the optional real-facts smoke tests additionally require the existing M1.2 temporary parsing tools (`php` and TypeScript installed locally or globally).

## 2. Data flow

```text
Explicit refresh(repo, store, adapter)
    -> Git ls-files --cached --others --exclude-standard -z
    -> supported tracked / non-ignored untracked source files on disk
    -> SHA-256 of actual working-tree bytes (not Git HEAD or staging area)
    -> compare with previous snapshot (content hash + language + parser identity)
    -> reuse unchanged immutable file-fact objects
       OR invoke extractor for changed/new files
    -> re-enumerate / re-hash to detect intervening source changes
    -> compare-and-swap publish new M1.4 snapshot
    -> return counts and bounded freshness assurance
```

Currently eligible language extensions: `.php`, `.ts`, `.mts`, `.cts`, `.tsx`; `.blade.php`, unsupported extensions, common generated directories and symlink files are excluded. This is **not complete language detection** or a comprehensive configurable ignore system. The temporary M1.2 integration supports only PHP and `.ts`-like TypeScript, not TSX; the parser-neutral fixture tests cover other eligibility cases.

## 3. Core guarantees demonstrated

| Property | Evidence | Qualification |
|---|---|---|
| Reopen persistent facts | M1.4 storage reused across refresh calls and test instances | New-process reload outside test process not separately benchmarked |
| No-op incremental extraction | Warm repeat: zero extractor invocations | Source files still re-enumerated, read and hashed twice |
| One changed file | Only changed file's callback invoked; unchanged record reused | Cross-file semantic edges not implemented |
| Git tracked / untracked / ignored | Real `git init`, `git add`, `git commit`, worktree fixture tests | Git root required; Git status and ignore semantics may change by Git configuration |
| Staged and unstaged precedence | Working-tree byte hash used, not staged content | Stage-only edits without working-tree content changes cause no re-extraction |
| Commit without byte change | Zero additional extractor calls | Git revision is not stored as a snapshot identity |
| Branch switch | File-content delta re-extracted; prior snapshot ID restored when content returns | No rename provenance or merge conflict support |
| Two actual worktrees | Independent checkout heads in same external store | Shared immutable object pool, separate checkout paths |
| Same-size/same-mtime edit | Hash mismatch detected | Entire contents read on every verification |
| Parser version drift | Cache identity change triggers affected file re-extraction | Test supplies identity; real grammar versions not yet verified |
| In-flight source change | Re-hash / re-enumerate rejects publication | A post-verification edit can still occur; this is point-in-time assurance only |
| Extractor failure | Previous head preserved | Explicit caller error, not automatic recovery |
| Unknown freshness on reopen | Store's `read()` reports `unknown` | No query path freshness verifier yet |

Important: the output label `content-hash-verified-before-publication` is a **point-in-time verification event**. It cannot guarantee that files remained unchanged *after* that check. It is not a permanent `READY` status and should not be presented as such to agents.

## 5. Self-review and discovered limitations

1. **Full hashing I/O**: a warm refresh reads every eligible file twice (initial scan + publication check), despite re-extracting none. The original goal concerns reducing repeated **agent file reads and parsing**, not pretending filesystem I/O is zero. A later, measured fast path may reduce I/O but must distinguish metadata checks from content verification.
2. **TOCTOU**: inventory validation is immediately before publication, not a filesystem-wide transactional snapshot. There is always a race between the final check and publication and afterward. Query-time freshness checks remain required.
3. **Limited language routing**: static extension allowlist, no `.gitattributes` overrides, shebang detection, JS or mixed-language container handling. Not a universal detector.
4. **Generated tracked files**: common generated folders are excluded even if explicitly tracked; should become a documented, configurable policy at a later gate.
5. **No parser fact proof**: the M1.2 smoke adapter is partial and known limited. Actual M1.3 Tree-sitter grammars must pass before M1.5 acceptance.
6. **No graph reconciliation**: no resolved edges, no relationship invalidation, no code impact analysis. File-fact cold/warm equality is *not* full graph equivalence.
7. **Persistence inherits M1.4 limits**: unhandled crash-orphaned locks, power-loss durability not established, no garbage collection, no large-repo performance measurements, no Windows test matrix.
8. **Process-level limits**: Git inventory launches a subprocess and has a 16 MiB result buffer; large monorepos need measured streaming/batching behavior before production.
9. **No silent stale success**: if source change is detected before publication, refresh errors explicitly. An already saved snapshot may remain readable but its freshness is `unknown`.
10. **No repo mutation**: indexing writes only into an external store. An explicit real Git status test confirms no tracked/untracked repository changes.

## 6. Milestone decision

**Accept M1.4.1 as a narrowly scoped feasibility spike only.** The tested design is sufficient to justify further prototyping of content-hash-driven reuse, but not enough to declare a production indexer or resume agent integrations.

**Next required gate:** complete M1.3 by installing pinned Tree-sitter dependencies and running all 12 real grammar tests; fix observed semantic extraction failures. Then M1.5 can connect accepted parser facts to storage/refresh and check cold vs warm **fact and relation graph** equivalence, parser upgrades, branch changes, concurrency and staleness.

No GitHub repository, branch, commit, PR, hook, or user agent configuration was modified in this work.
