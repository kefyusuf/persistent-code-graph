# M1.6.4 — Canonical Verified Query Migration

Status: **local offline candidate; full CI acceptance pending**.

## Decision and scope

Relocate the existing M1.4.2 single-query and M1.5.1 batch-query implementation, without rewriting the algorithm, to `src/query/query.mjs`. This is a code-ownership refactor only. It introduces no new operation, parser, graph edge, background refresh, agent integration, service, or storage schema.

## Implementation ownership

- `src/query/query.mjs` owns `verifiedQuery` and `verifiedQueryBatch` and imports the existing `src/storage/store.mjs` and `src/incremental/inventory.mjs` modules.
- `src/core.mjs` invokes the canonical module; its public pipeline query and queryBatch contracts are unchanged.
- `spikes/m1.4.2/src/query.mjs` re-exports the canonical module. `spikes/m1.5.1/src/batch.mjs` re-exports the same canonical batch function. Existing callers retain function identity.
- M1.6.2 and M1.6.3 ownership assertions now inspect the canonical query module, not the compatibility shim.

## Preserved behavior and limitations

1. An explicitly requested query is read-only and requires an explicit parser identity.
2. A missing or stale snapshot does not return old symbol observations; any source-inventory error produces `unknown` rather than a false verified answer.
3. Two eligible-source content-hash scans and an index-head check bracket response construction. The assurance is point-in-time only; no promise is made about mutations after the final check.
4. Single-query filters and per-request limits remain bounded. Batch requests retain a maximum of eight entries and a separate aggregate result budget.
5. References remain unresolved observations. Coverage remains partial; a result not found in indexed facts is **not** proof of global absence.
6. No change to snapshot format, parser/extractor cache identity, eligible file rules, or refresh behavior.

## TDD and regression evidence

- **RED:** new query-migration suite fails to load the missing `src/query/query.mjs` module.
- **GREEN:** seven query migration tests pass after moving the unchanged implementation and replacing old modules with strict re-export shims.
- **REGRESSION:** the original M1.4.2 query and M1.5.1 batch suites remain green. All 147 local offline tests passed after updating M1.6.2/M1.6.3 source-ownership assertions.
- **ACCEPTANCE:** run `node tools/verify-gates.mjs --mode full` in CI with committed lockfiles. Expected composition: 147 offline + 16 real grammar/integration tests = 163. **Do not mark this milestone accepted or merge it until CI confirms the actual counts and no skipped tests.**

## Known risks

- Each query still rereads and hashes eligible files twice; this migration does not optimize I/O or prove token savings.
- The gate does not prevent a file from changing after verification completes.
- Windows durability, simultaneous-process lock recovery and semantic cross-file resolution remain out of scope.
- The historical `spikes/` consumers retain compatibility shims until a later cleanup gate explicitly removes them.

## Next step

Once CI is green and review is complete, consider a separate compatibility-cleanup gate with an explicit consumer inventory and removal policy. Do not use this query refactor as justification to add MCP, a daemon, vector search, or other scope extensions.
