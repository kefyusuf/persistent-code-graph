# M1.5.2 — Reproducible Parser Acceptance Runner

**Date:** 2026-11-01  
**Decision:** ACCEPT the offline acceptance-runner infrastructure; keep M1.3 and M1.5 real Tree-sitter gates **BLOCKED**.  
**Scope:** A test orchestrator and GitHub Actions workflow only. No product runtime feature, new parser, index format, MCP, or background operation.

## Why this milestone exists

The available environment repeatedly fails npm resolution (`curl: (6) Could not resolve host: registry.npmjs.org`). This is an environment blocker, not evidence that PHP, TypeScript or TSX grammar extraction is correct. Repeatedly developing more offline features would defer the acceptance criterion indefinitely.

The solution is to package the tested baseline with an explicit, fail-closed grammar gate that can run on a clean machine or GitHub Actions runner with access to npm.

## Acceptance contract

`node tools/verify-gates.mjs --mode offline` executes 8 suites; successful result is **OFFLINE_ONLY**, never `PASS`. `--mode full` executes those suites and, only if they pass, checks pinned parser dependencies and executes both real parser suites (12 M1.3 grammar tests and 3 M1.5 integration tests).

- Missing parser dependencies: `BLOCKED`, exit 2, no false success.
- Failed tests, incomplete TAP output, skipped/cancelled cases: `FAIL`, exit 1.
- All suites pass: `PASS`, exit 0 — code-level grammar acceptance evidence (not production maturity).
- Invalid arguments: exit 64.
- Per-suite `node --test` runs from the original spike directory, so fixture resolution remains unchanged.
- A JSON manifest plus a log per suite are written locally. The report contains each test count and status; it does not generate artificial test counts.
- A separate CI rule requires the npm dependency **lockfile be committed** before the run counts as reproducible acceptance.

The parser runtime and WASM grammar package versions remain exact, `web-tree-sitter@0.27.1` and `tree-sitter-wasm@2.0.4`. Pinning the direct dependencies is not equivalent to having a committed npm lockfile. In a bootstrap CI run, npm generates the lockfile and the workflow attaches it to the evidence artifact. The CI reproducibility check fails until the lockfile is committed.

## Verification conducted locally

- All previous 115 offline tests pass.
- 6 additional test-runner contract tests pass.
- **121/121 offline tests pass**; `OFFLINE_ONLY` is correctly reported.
- Full verification again reports **BLOCKED**, exit code 2, because the actual WASM packages are missing; no grammar suite is represented as a success.
- The real grammar acceptance total remains **15 unexecuted tests** (12 M1.3, 3 M1.5).
- CI workflow is present but **has not been executed** on GitHub.

## Next gate and handoff

A remote GitHub repository is now operationally useful: it provides a clean, network-connected test runner and retains a visible acceptance history. When the repository is created, add this baseline on a dedicated branch; generate and commit `spikes/m1.3/package-lock.json` from a network-connected environment; run the workflow; investigate any genuine AST mismatches; complete a reproducible green CI run. Only after that milestone should the temporary parser be retired or M1.6 scope defined.

## Architectural self-review

1. The acceptance runner does not depend on any particular programming-language implementation of the future indexing engine.
2. A failing preflight makes the actual parser gate blocked, not passed.
3. CI follows least-privilege `contents: read`; it neither writes source nor deploys.
4. Tests remain stage-scoped instead of being copied or reformulated.
5. No token savings or semantic-graph claims are inferred from test harness success.
6. Current gap: CI has not run and the actual grammar compatibility remains unknown; Windows and supply-chain pinning of GitHub Actions themselves are future verification needs, not addressed here.
