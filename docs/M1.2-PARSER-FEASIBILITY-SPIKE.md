# M1.2 — Parser Feasibility Spike: Two Distinct Languages, One Fact Contract

**Project:** Persistent Code Graph (working title)
**Date:** 2026-11-01
**Status:** Partially verified (11/11 local probe tests pass; production parser validation blocked)
**Milestone:** M1.2, not M1 production implementation
**Dependencies:** M0.1, M0.2, M1.0, M1.1
**Decision scope:** Parser feasibility and fact normalization only. No language/runtime/database commitment.

## 1. Goal and hypothesis

Determine whether two languages with meaningfully different syntax can produce source-backed, deterministic **file-local facts** without contaminating the shared graph schema with language-specific assumptions.

Hypothesis: a small adapter boundary can retain syntax-backed declarations, raw reference occurrences, precise byte ranges, and coverage/diagnostics across PHP and TypeScript. It must not need an LLM, semantics-by-name guessing, external index service, agent integration, or a database.

This spike deliberately avoids implementing the persistent index, relation resolver, Git lifecycle, full M1.1 schema, or MCP service.

## 2. Environment and actual parser backends

- Node.js: v22.16.0
- TypeScript compiler API: v5.8.3 (locally available)
- PHP CLI tokenizer: v8.4.24 (locally available)
- Tests: Node's built-in test runner; no downloaded test framework.
- **Tree-sitter: NOT executed.** Its packages were not installed. An attempt to fetch the runtime/grammars through pip failed due to unavailable DNS/network access. No claim is made about grammar equivalence, AST node names, Tree-sitter dialect behavior, packaging or install portability.

The chosen temporary backends are **experiment instruments**, not recommendations for the M1 production parser. PHP's native tokenizer is not a robust PHP parser; TypeScript's compiler API is language-specific and couples extraction to the TS runtime.

## 3. Spike architecture

```text
TS source ── TypeScript Compiler AST ─────┐
                                          ├─ adapter facts ── normalized FileFacts
PHP source ─ PHP native token_get_all ────┘             │
                                                        └─ tests + canonical JSON-like result
```

Normalized subset (not an authoritative database schema):

```text
FileFacts {
  file, language, contentHash,
  declarations[] { id, kind, name, languageSyntaxKind, range },
  references[] { id, role, spelling, alias?, module?, resolutionStatus?, range },
  relations: [],
  diagnostics[],
  coverage { declarations, references, calls }
}
```

`range` contains `[startByte, endByte)` in UTF-8 bytes plus one-based display lines. IDs depend on file path, file hash, role/name and byte offsets; they are deterministic for the same file bytes and deliberately **not cross-snapshot-stable IDs**. The full M1.1 parent/scope/source metadata, snapshot ID and persistence remain implementation tasks.

All raw calls remain unresolved. No calls/implements edges are synthesized by name matching.

### Verified tests

1. `SYM-002` analogue: TypeScript duplicate interfaces remain two declaration occurrences.
2. TypeScript import specifier and alias remain distinct from call-reference spelling; no synthetic resolved call edge.
3. PHP trait, class and method are extracted, while trait-use and adaptation remain raw syntax occurrences.
4. `SYM-009` subset: astral Unicode before a TypeScript declaration preserves UTF-8 byte offsets.
5. `SYM-010` subset: malformed TypeScript produces a diagnostic and non-full coverage.
6. Repeated extraction is deterministic on identical input.
7. PHP `use ... as ...` at namespace scope does not incorrectly become trait adaptation.
8. Unresolved PHP `$this->missing()` remains a reference occurrence, not a fabricated resolved edge.
9. Malformed PHP yields an explicit tokenizer parse diagnostic.
10. Same-named nested TypeScript functions are not collapsed into one record.
11. The limited PHP/TypeScript adapters are not labeled as fully supported, and malformed PHP is `failed`.

## 5. Findings and decisions

**F-01 — The common fact contract is feasible in a limited subset.** Two different parsing technologies can produce common records while preserving the original syntax information in `languageSyntaxKind` and roles. This is a positive *interface* signal, not proof of general parser correctness.

**F-02 — Raw references must be first-class.** Both languages show why `observed call` and `resolved call edge` need separate representations. Unresolved is informative; invented confidence is harmful.

**F-03 — Syntax context can be misclassified even in a small example.** A bare `as` token means different things in PHP. The added failing regression test detected a false-positive trait-adaptation occurrence. A production adapter should use AST node context, not ad hoc token scopes.

**F-04 — Byte offsets require deliberate conversion.** TypeScript offsets use JS string indexing (UTF-16 code units); they must be converted to UTF-8 byte offsets for the common contract. The fixture with an astral character exercises this.

**F-05 — A runtime-independent production parser has not been selected.** A shared pinned Tree-sitter runtime and per-language grammars remain promising, but their real outputs, parser error behavior, and local deployment compatibility need a separate successful experiment. Official upstream documentation confirms the relevant grammars exist; that is not equivalent to executing them here.

**F-06 — A simplistic PHP tokenizer extractor must not become the core.** It exists to test adapter boundaries and reveal mistakes. It lacks complete namespace resolution, closures, attributes, interpolated code, nesting, and grammar error recovery semantics. Its method detection is insufficient for production correctness.

## 6. Gate assessment

| Gate | Status | Evidence or blocker |
|---|---|---|
| Two different languages output normalized syntax facts | PASS (subset) | 11/11 tests |
| No fabricated definite call links | PASS (tested cases) | Empty relations with raw call occurrences |
| Deterministic and source-backed output | PASS (tested cases) | Repeated extraction + ranges |
| Syntax error diagnostics surfaced | PASS (tested cases) | Broken PHP and TS fixtures |
| Tree-sitter grammar execution and pinned versions | BLOCKED | Packages absent; DNS unavailable |
| Complete per-file scope and relation extraction | NOT IN SCOPE | M1 implementation work |
| Full M1.1 declaration/reference schema | NOT COMPLETE | Optional fields, ownership/snapshot/coverage rules not fully implemented |
| Initial persistent index and reopening | NOT STARTED | M1 main implementation |
| Incremental refresh, Git integration and MCP | NOT STARTED | M2/M3/M5 respectively |

**Milestone decision:** Keep M1.2 as **PARTIALLY VERIFIED**. Do not claim the production parser is ready. Do not start M2/MCP or introduce a database on the basis of these results.

## 7. Proposed next step — M1.3 Parser Compatibility Gate

1. Acquire a vetted, reproducible Tree-sitter runtime and both PHP/TypeScript grammars without implicit downloads at runtime.
2. Run independent same-fixture Tree-sitter extraction tests and inspect actual CST nodes before writing queries.
3. Preserve exact source-byte ranges, duplicate declarations, import aliases, trait-use syntax, unknown-call occurrences and parse diagnostics.
4. Add a coverage report with `supported / partial / unsupported / failed` for the explicitly claimed constructs.
5. Record parser/grammar build identity in cache invalidation inputs; test that version changes invalidate only affected cache slices where feasible.
6. Decide the M1 implementation language/parser path from observed compatibility and deployment complexity, **not** existing developer preferences.

M1.3 should remain a bounded parser gate. Persistence, file watching, PR review, cloud services, embeddings and agent memory are explicitly excluded.
