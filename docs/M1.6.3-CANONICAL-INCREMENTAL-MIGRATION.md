# M1.6.3 — Canonical Inventory and Refresh Migration

Status: **implementation verified in GitHub Actions (156/156 at implementation commit `4390cdbd`); Draft PR review and final-head CI remain required**.

## Scope and decision

Move the existing M1.4.1 working-tree inventory and explicit incremental refresh implementations to `src/incremental/` without changing their behavior, persistent record representation, or published API. The indexed source set remains tracked/staged/dirty and eligible untracked files, excluding ignored untracked files and unsupported dialects. `git ls-files` discovers candidates, while the **working tree bytes** determine the indexed facts.

This change is a code ownership refactor, not a new incremental algorithm. No watches, hooks, background processes, automatic refresh, semantic relation resolution, or new languages are added.

## Ownership and compatibility

- `src/incremental/inventory.mjs` owns `classifySource`, `inventoryGitCheckout`, and `verifySourceInventory`.
- `src/incremental/refresh.mjs` owns `refreshFileFacts` and the test-only `fixtureExtractor`. It imports the canonical `src/storage/store.mjs` directly.
- The two historical M1.4.1 modules are **re-export-only shims**, preserving strict function identity for existing importers.
- `src/core.mjs` calls canonical refresh directly. `src/parser/provider.mjs` and the still-experimental verified query module import the canonical inventory directly.
- The verified query module itself remains in `spikes/m1.4.2/` until the next separately gated migration.

## Preserved invariants

1. Tracked, staged, modified, and eligible untracked sources come from working-tree bytes; symlinks are not followed. Unsupported paths, templates, and ignored untracked files remain excluded.
2. Deterministic NUL-delimited Git path handling and SHA-256 byte hashes remain unchanged.
3. Unchanged content and compatible parser identity reuse the previous file-facts record. Parser identity changes force re-extraction for affected files.
4. Immediately before publication, `verifySourceInventory` rechecks the entire eligible source set; observed drift rejects publication.
5. The storage layer's optimistic head check and atomic snapshot publication behavior are unchanged. A failed extraction or verification does not replace the previous head.
6. Source freshness is a point-in-time assertion only. A persisted snapshot is not implicitly current; verified reads revalidate source content.

## Limitations / explicit non-goals

- Entire eligible source inventory is still rehashed on each refresh; verified queries still perform two scans. Zero reparse is not zero I/O.
- A filesystem mutation after the final verification is not prevented. The subsequent query must recheck freshness.
- Crash-safe writer-lock recovery, Windows behavior, filesystem durability, and multi-process race semantics are not proven by this refactor.
- This is a file-facts index; no verified cross-file call-target resolution or agent integration is claimed.
