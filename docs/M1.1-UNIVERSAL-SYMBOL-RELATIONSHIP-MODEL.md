# M1.1 — Universal Symbol and Relationship Model

**Working title:** Persistent Code Graph  
**Status:** Proposed technical contract; no code authorized by this document  
**Stage:** M1 — Modeling and fixture design  
**Predecessors:** M0.1 Product Definition; M0.2 Architecture Constraints; M1.0 Language Detection and Structural Extraction Architecture  
**Decision scope:** Source-backed facts and normalized graph identity, not programming language, database, CLI implementation, or framework selection.

## 1. Goal

Represent structural facts from different languages in one deterministic, persistent, queryable model **without equating different language semantics** or guessing cross-file bindings. Preserve exact source declarations, references, provenance, coverage and ambiguity. This schema is an intermediate *logical contract*, not a physical SQL schema or a public API commitment.

The first M1 implementation still indexes **one language**. The contract must withstand small fixture tests from another language before being frozen for M2.

### Non-goals of this milestone

Do not implement parsers, language services, type-checking, cross-language runtime linking, graph databases, cloud access, embeddings, visualization, PR bots, agent memory, IDE extensions, automatic hooks or MCP transport. Do not claim compiler-equivalent correctness.

## 2. Core decision: declaration first, logical symbol later

The authoritative basic unit is a **source declaration occurrence**. It lives at one file/range, even if several declarations jointly describe one logical language symbol. This avoids losing locations or collapsing legal overloads and merged/partial declarations.

- **Declaration:** An individual syntax-backed definition, e.g. one `interface Box` block or one C# `partial class User` block.
- **Reference occurrence:** An actual appearance of a name, import specifier, type name or call site, tied to a source range; it may have no known target.
- **Resolved relationship:** A proven or explicitly tentative association between supported endpoints, with evidence and resolution level.
- **Logical symbol grouping:** A *future derived view* only where language rules and module/project boundaries justify it; no mandatory synthetic merged-symbol nodes in M1.

A declaration and its logical identity are **not** interchangeable. Display names and qualified names are not globally unique identifiers.

## 3. Minimal logical records

Only five record families are required at this stage; some are already defined in M0.

| Record | Minimum fields | Notes |
|---|---|---|
| `Snapshot` | `snapshotId`, `checkoutId`, `manifestId`, `indexSchemaVersion`, `parserSetId`, `configId`, `publicationState` | Published graph boundary; no partial publication. |
| `SourceFile` | `fileId`, `relativePath`, `contentHash`, `languageId`, `dialect?`, `parserIdentity`, `coverage`, `diagnostics[]` | File identity is checkout/snapshot scoped. |
| `Declaration` | `declarationId`, `fileId`, `kind`, `languageSyntaxKind`, `name`, `qualifiedName?`, `parentDeclarationId?`, `range`, `modifiers?`, `signature?`, `evidence` | One source occurrence, never a name-only aggregate. |
| `ReferenceOccurrence` | `referenceId`, `fileId`, `ownerDeclarationId?`, `role`, `spelling`, `range`, `rawTarget?`, `evidence`, `resolutionStatus` | Call expressions/imports/type mentions exist before linking. |
| `Relation` | `relationId`, `sourceId`, `targetId`, `kind`, `evidenceReferenceId?`, `resolutionLevel`, `sourceRange`, `provenance` | Edges require supported endpoints and explicit evidence. |

`Snapshot` also references a repository/checkout manifest as already specified in M0. This is not a requirement for a sixth independently mutable subsystem.

### Source range convention

- Use zero-based, UTF-8 byte offsets in half-open intervals `[startByte, endByte)` as the canonical parser-neutral coordinate. Required: `startByte`, `endByte`.
- Record one-based start/end line numbers for agent-facing display; columns, if exposed, must declare their unit (UTF-8 bytes vs Unicode code points). Do not silently mix units.
- `relativePath` is normalized relative to an explicit repository/checkout root using `/`; never use an absolute path as the cross-machine identity.
- A location belongs to the **source bytes of the recorded file content hash**. An old snapshot's range may not be used as a new snapshot's location.
- Generated bodies are *not* copied into graph records by default. Source snippets, if later supported, must be fetched from the verified matching file snapshot with bounded length.

## 4. Declaration vocabulary and language fidelity

### Small normalized `kind` vocabulary

`module`, `namespace`, `class`, `interface`, `trait`, `struct`, `enum`, `function`, `method`, `type`, `constant`, `field`, `variable`, `implementation_block`, `other`.

This is a **category index**, not a statement that a Rust trait and a PHP trait have identical semantics. `languageId` + `languageSyntaxKind` preserves their distinct meaning. A source declaration also retains minimally necessary language-specific metadata, in a namespaced, schema-versioned key/value area. Unknown fields must not influence core identity or query behavior.

`implementation_block` is an explicitly proposed refinement of the M1.0 vocabulary, justified by Rust `impl` constructs that associate methods with a type and optionally a trait. It is **not** a general purpose plug-in type system. `field` and `variable` are similarly small categories needed for ordinary definition lookup; unsupported adapters may omit them.

### Shape examples (conceptual, not code)

```json
{
  "fileId": "f:...",
  "declarationId": "d:...",
  "languageId": "rust",
  "kind": "implementation_block",
  "languageSyntaxKind": "trait_impl",
  "name": "impl Display for Invoice",
  "qualifiedName": null,
  "range": {"startByte": 120, "endByte": 310},
  "metadata": {"rust.traitPath": "Display", "rust.selfTypePath": "Invoice"},
  "evidence": {"origin": "parser", "grammarId": "...", "extractorId": "..."}
}
```

Rust's inherent `impl Invoice {}` and trait `impl Display for Invoice {}` must not be conflated. A syntax-backed implementation block exists even when precise trait/type resolution is unavailable. The name in this example is a human-facing label, not a reliable identity key.

### What is intentionally not normalized away

- PHP `trait` composition and adaptation (`insteadof`, `as`) are not Rust trait implementation.
- A C# `partial class` source declaration is not automatically merged into another file's declaration.
- A TypeScript interface with the same name may participate in language-specific declaration merging; same-name alone is insufficient outside the correct module/scope.
- Rust macro invocations and conditional compilation do not imply that the static source contains the full expanded program.
- Python decorators/dynamic attribute assignments do not imply a known concrete call target.

## 5. Reference occurrences precede resolution

A raw reference is a first-class, source-backed fact independent of the resolver. Minimum `role` examples:

- `call`, `type_use`, `read`, `write`, `import`, `export`, `inheritance_target`, `interface_target`
- `php.trait_use`, `php.trait_adaptation`
- `rust.impl_self_type`, `rust.impl_trait`
- `csharp.partial_type_part`, `typescript.declaration_augmentation` (only when the grammar actually identifies such syntax)

A role may be language-specific; it does not automatically authorize a semantic edge. `spelling` is the exact source form; `rawTarget` may be a syntactic path or unqualified identifier. Neither is necessarily a resolved target.

**Resolution states:**

| State | Meaning | Allowed relation behavior |
|---|---|---|
| `unresolved` | No defensible unique binding | Keep occurrence; do not emit a fabricated concrete edge |
| `ambiguous` | Several plausible bindings, none proven | Keep occurrence and optionally bounded candidate IDs; no definite edge |
| `inferred` | A candidate is supported by a documented heuristic | Optional edge explicitly labelled `inferred`, never `resolved` |
| `resolved` | Binding is supported by the declared resolver's actual evidence and coverage | Edge may be emitted as `resolved`; this still does not assert runtime dispatch certainty |

`resolved` must state **what** was resolved: a lexical import binding, static symbol reference or runtime target are different claims. A static call target is not proof of the callee executed at runtime.

## 6. Relation vocabulary and evidence

M1.0's baseline relation names remain `contains`, `imports`, `exports`, `references`, `calls`, `extends`, `implements`. M1.1 does **not** require implementation of all of them in M1.

**Rules:**

1. `contains` can link syntax-backed declarations within one file/scope when the parent is unambiguous; source scopes may also be reconstructed via parent IDs.
2. A source `call` occurrence does not by itself create a `calls` edge to a same-named method elsewhere.
3. `imports` and `exports` may be recorded as raw references when module resolution is unsupported; do not invent remote nodes.
4. `implements` must declare language-specific semantics; it is not the generic edge for both PHP trait use and Rust trait implementation.
5. If a future language fixture requires an additional relation kind (`uses_trait`, `declares_for`, `merged_with`), add it only with documented semantics, tests, and a schema compatibility decision. For M1, retain the source occurrence and defer the relation.
6. `Relation` stores the exact evidence source occurrence and resolution method/level. Relations without valid current snapshot endpoints must fail integrity validation.
7. Store direction explicitly. E.g. `source calls target`; reverse callers are a query, not a second semantic edge.

A relation can be backed by syntactic evidence or resolver output, but always points back to a source location and parser/resolver identity.

## 7. Deterministic identity and ordering

- **Snapshot identity:** Hash of a canonical eligible-file manifest (paths + content hashes), parser/extractor/config/schema identities and checkout isolation key. Different checkout instances remain isolated even when their bytes coincide.
- **File identity within snapshot:** Deterministically derived from snapshot/checkout context and canonical relative path.
- **Declaration identity:** Deterministically derived from file identity, syntax role, exact byte range and disambiguating local anchor. Include syntax kind and an occurrence discriminator where needed; never derive solely from `qualifiedName`.
- **Reference identity:** Deterministically derived from file identity, role and exact source span.
- **Relation identity:** Deterministically derived from kind, source/target identities, evidence occurrence and declared resolution method. Multiplicity of legitimate call sites must be retained.
- **No guaranteed cross-snapshot ID stability:** A rename, edit or earlier insertion may legitimately change IDs. Query results may offer human-friendly qualified names and ranges, but must not invent a stable identity across rewrites.
- Canonical sorting: normalized path, byte range, category/role, then ID; serialize maps/sets deterministically before hashing.

Versioning is explicit; parser/grammar changes that alter syntax fact meaning invalidate affected extraction caches. Index schema changes require migration or rebuild, never silent reinterpretation.

## 8. Coverage and diagnostics

Coverage is **per file, per feature**, not just a project-wide language label. Proposed feature keys: `declarations`, `imports`, `references`, `calls`, `inheritance`, `implementation`, `merging`. Values: `supported`, `partial`, `unsupported`, `failed`.

`Supported` means the adapter supports its **documented construct subset**, not exhaustive compiler semantics. A coverage report also lists relevant exclusions/limitations (e.g. unresolved dynamic access, macros, templated embedded languages).

Diagnostics record at least `code`, `severity`, `range?`, `languageId`, and a concise reason. Parse errors may yield partial syntax-backed facts outside error spans if the parser can guarantee their ranges; those facts are marked partial. Structural corruption, invalid references or incomplete atomic publication is a failed refresh, not a partial current graph.

Keep **freshness** separate from **coverage**: a perfectly current graph may have unsupported constructs, and a formerly complete graph may now be stale.

## 9. Language stress cases and required behavior

### 9.1 TypeScript declaration merging

```ts
interface Box { height: number }
interface Box { width: number }
```

Record two distinct declarations, both with their own positions. Do not collapse them into one record. A later type-aware resolver may derive a group **within the appropriate scope/module**. Source: TypeScript Handbook, Declaration Merging.

### 9.2 C# partial type

`Models/Order.Part1.cs` and `Models/Order.Part2.cs` each declare `partial class Order`. Record two declarations with separate `fileId` and precise ranges, retaining `partial` modifiers. A later project-aware grouping must verify namespace, enclosing type, assembly/project context and signature constraints. No provisional group may be treated as a proven merged type. Source: Microsoft Learn, Partial Type.

### 9.3 PHP trait use

```php
trait TracksEvents { public function emit() {} }
class Order { use TracksEvents; }
```

Record trait/class declarations and a `php.trait_use` reference occurrence. Without a qualified binding resolver, do not connect the class to the trait by a simple name guess; do not use a Rust `implements` semantic label. Trait adaptation and precedence must not be synthesized without evidence. Source: PHP Manual, Traits.

### 9.4 Rust impl blocks

```rust
trait Render { fn render(&self); }
struct Order;
impl Render for Order { fn render(&self) {} }
impl Order { fn id(&self) -> u64 { 1 } }
```

Record the trait, struct, two distinct `implementation_block` declarations, contained methods and raw `rust.impl_trait` / `rust.impl_self_type` occurrences. A trait impl and inherent impl must remain distinguishable even before type resolution. Source: Rust Reference, Implementations.

### 9.5 Python shadowing and dynamic behavior

Two functions with the same local name in different nested scopes are distinct declaration occurrences. Imported aliases and decorated callables may have runtime behavior that cannot be resolved from syntax alone. No cross-scope call edge from a bare matching name.

### 9.6 JavaScript / TypeScript import alias

`import { save as persist } from './storage'` produces a source import occurrence including original/exported spelling and local binding alias. A call `persist()` must not resolve until module/export and lexical scope facts justify it. TSX/JSX source ranges must use the selected dialect grammar.

## 10. Incremental graph implications (future M2 behavior)

A file's extraction cache contains its declarations, reference occurrences and syntax diagnostics. When that file changes, the system replaces its entire file-local fact slice; unchanged files reuse their cached slices. It then resolves any cross-file relations affected by changed exported names, imports, type paths or scopes.

**M2 correctness-first allowance:** Re-run all relation resolution on the combined cached facts rather than immediately implementing a dependency-aware incremental resolver. This still avoids reparsing unchanged files. Record the amount of re-resolution as a separate performance metric.

Deletion/rename requires retiring old file-local declarations and every affected edge. A failed update preserves the last internally consistent snapshot but must make the freshness state visible. Atomic publication and the clean-build equivalence invariant remain mandatory.

The graph must never mix source ranges from different file hashes in one supposedly verified snapshot.

## 11. Minimal acceptance fixtures (design-level, not code implementation)

| ID | Fixture | Required assertion |
|---|---|---|
| `SYM-001` | Two same-named functions in distinct scopes | Two declaration IDs, two ownership scopes; no name-based collapse |
| `SYM-002` | TS duplicate interfaces | Two declarations and two precise ranges; no automatic synthetic merge |
| `SYM-003` | C# partial class in two files | Two source-backed declarations; project-aware grouping deferred |
| `SYM-004` | PHP trait use and alias | Retain trait-use/adaptation occurrences, not Rust `implements` |
| `SYM-005` | Rust trait impl + inherent impl | Two distinct implementation blocks, raw type/trait references |
| `SYM-006` | Python unknown dynamic call | Reference exists; no fabricated `resolved` call edge |
| `SYM-007` | JS/TS import alias | Both import spelling and local binding retained |
| `SYM-008` | Function overloads / duplicate signatures | Separate declarations and source ranges; signatures not name-collapsed |
| `SYM-009` | UTF-8 content + CRLF | Exact byte spans and normalized display line numbers |
| `SYM-010` | Parser error region | Partial/failed coverage explicitly reported; no false certainty |
| `SYM-011` | One file edit vs fresh build | Canonical graph equality and no reparse of unchanged compatible files (M2) |
| `SYM-012` | Deletion / rename | No dangling active edges or stale source locations (M2) |
| `SYM-013` | Graph refresh interruption | Old snapshot readable but freshness/status not falsely current (M2) |
| `SYM-014` | Two agents querying same snapshot | Same evidence and stable bounded order (M5) |

**Implementation gate:** M1 begins with a chosen language and fixture subset `SYM-001`, `SYM-006` (or the language-appropriate unresolved-reference equivalent), `SYM-009`, and `SYM-010`. Other language fixtures initially validate the *design* and become executable as adapters are implemented. Do not require full support for five languages to complete M1.

## 12. Query and presentation budget

No automatic full-file or whole-repository context injection. A future query returns `snapshotId`, `freshness`, `coverage`, bounded results, result count/cursor and precise source locations. An unresolved reference is useful: show the observed name and location, not an invented edge. Identical queries against the same snapshot must have deterministic ordering.

M1 CLI may expose only `status`, `files` and `definitions` (or equivalents), sufficient to prove the persisted model. Caller/callee and impact queries belong to M4; MCP belongs to M5.

## 13. Compatibility with previous decisions / deliberate deltas

- Preserves M0 invariants `INV-01` through `INV-12`: source authority, persistence, offline core, deterministic, evidence, freshness, atomicity and checkout isolation.
- Preserves M1.0's separation of language detection, extraction and semantic resolution.
- **Refinement A:** Make `Declaration` and `ReferenceOccurrence` explicit rather than representing every raw reference as a committed semantic edge.
- **Refinement B:** Expand the small normalized declaration-kind vocabulary with `implementation_block`, `field` and `variable` to prevent source-structure loss; the core remains closed and language-specific meaning stays in namespaced metadata.
- **Refinement C:** Defer merged logical-symbol nodes until needed by a concrete, evidence-backed resolver. In M1, distinct occurrences are the canonical truth.
- **Refinement D:** Add `ambiguous` as a reference resolution state alongside resolved/inferred/unresolved; it is not permission to invent edges.
- **No new subsystem:** This is a data-contract refinement, not approval for LSP, type checking, graph DB, semantic search or new background services.
